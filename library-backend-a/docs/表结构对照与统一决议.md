# 表结构对照与统一决议清单（A ↔ B）

> **用途**：全组对齐 MySQL 表结构的议题底稿。会后逐条拍板，把结论写进唯一一份 MySQL DDL（建议以 B 的 `database/migrations/mysql/` 为底座修订），此后所有人（含 A 的 SQLite 适配）按同一份 DDL 开发。
> **底稿来源**：A = `library-backend-a/docs/schema.sql`（9 表，需求文档 V1.2 口径）；B = `database/migrations/mysql/001_backend_b.sql` + `002_demo_catalog.sql`。
> **总体结论**：9 张表两边一一对应、**无缺表**；差异集中在字段增减与状态枚举，其中 **D1/D3/D8 三条不统一就无法联调**。

## 一、全局约定（建议直接采纳 B 的现状）

| # | 项 | A 底稿 | B 现状 | 建议 |
|---|---|---|---|---|
| G1 | 引擎/字符集 | SQLite | InnoDB + utf8mb4_unicode_ci | ✅ 采纳 B，这是 MySQL 基线 |
| G2 | 主键类型 | INTEGER | BIGINT UNSIGNED AUTO_INCREMENT | ✅ 采纳 B |
| G3 | 枚举大小写 | 大写（`AVAILABLE`/`BORROWED`…） | 小写（`available`/`borrowed`…） | ⚖️ **二选一**，建议**小写**（SQL 惯例）；两边都是常量/字面量的机械替换，成本相当 |
| G4 | 时间类型 | TEXT 存 `yyyy-MM-dd` | DATETIME | ⚖️ 建议：业务日期（借出/应还/归还）用 **DATE**（需求只有天粒度，逾期天数=日期差）；记录时间（created_at/updated_at）用 DATETIME |

## 二、逐表对照（9 张）

| 表名（建议沿用 B） | A 底稿 | B 现状 | 差异与建议 |
|---|---|---|---|
| `users` | name / status TEXT | display_name / active TINYINT / updated_at | ✅ 以 B 为准；D7 |
| `readers` | card_no / status / registered_at | reader_no / **user_id 关联 users** / active / updated_at | ✅ 以 B 为准（B 的 user_id 关联是个人中心 1.3.15 必需的，A 底稿缺）；命名 card_no→reader_no |
| `categories` | + description / created_at | 仅 id+name | ⚖️ 建议 B 加 description 列（分类管理页需要，10 分钟事） |
| `books` | intro / cover_path / **status(下架)** / publish_date / 业务层 ISBN 校验 | publish_year / **ISBN 全局 UNIQUE** / 无 status/intro/cover_path | 🔴 D4/D5：B 需补 3 列 |
| `book_copies`（A 叫 copies） | barcode / **location / acquired_date** / **5 态状态机** / updated_at | copy_code / **仅 3 态** / 无位置入藏列 | 🔴 **D1（最硬）**：需求 2.2 状态机明确 5 态，B 的 3 态 ENUM 装不下"预约保留/维修中" |
| `loans`（A 叫 borrow_records） | + **book_id / status / renew_count** / 唯一约束用部分索引 | 仅 copy_id/reader_id；唯一性用生成列技巧（✅ MySQL 正确做法） | 🔴 D2：续借功能需要 renew_count；按书查借阅需要 book_id；部分索引 MySQL 不支持，用 B 的生成列方案 |
| `reservations` | **queue_no / pickup_deadline / 5 态** | 3 态（waiting/fulfilled/cancelled）/ 无排队号 | 🔴 **D3（最硬）**：需求 4.2 预约全流转（排队→待取→完成/失效顺延）必须有 queue_no + 待取截止 + EXPIRED 态 |
| `system_params` | key/value；键名 loan_period_days / loan_limit / max_renew_count=2 | param_key/param_value/description；键名 borrow_period_days / borrow_limit / max_renew_times=1 | 🔴 **D8**：键名与默认值两边不一致，B 的 `key` 列名在 MySQL 是保留字风险，建议整体采纳 B 的列名 |
| `operation_logs` | + operator_name / op_type | operator_user_id / action_type | ⚖️ 以 B 为准 + 可选加 operator_name 列（免 JOIN，A 建议加） |

## 三、决议清单（会上逐条拍板）

| 编号 | 决议点 | A 建议方案 | 影响 |
|---|---|---|---|
| **D1** 🔴 | 副本状态扩为 5 态：`available / borrowed / reserved(预约保留) / maintenance(维修中) / lost(遗失报损)`；补 `location`、`acquired_date` 列 | 需求文档 2.2 白纸黑字，无讨论空间 | B 改 ENUM；C 的借阅/归还原样兼容 |
| **D2** 🔴 | `loans` 补 `book_id`、`status`、`renew_count` 三列 | renew_count=续借次数（4.2 要求）；book_id 免联查；status 可选（也可由 returned_at 推导，二选一） | B 加列；A/C 读写 |
| **D3** 🔴 | `reservations` 补 `queue_no`、`pickup_deadline`，状态扩为 5 态（waiting/ready_to_pick/finished/cancelled/expired） | 需求 4.2 预约全流转，无讨论空间 | B 改；C 实现流转 |
| D4 | books 补 `intro`、`cover_path`、`status`（active/shelved_off 下架=逻辑删除）；出版日期用 `publish_date DATE`（需求原文"出版日期"），年份筛选取 `YEAR()` | 需求 2.2 图书表字段清单原文 | B 加 4 列 |
| D5 | ISBN 唯一性：**数据库全局 UNIQUE（B 现状）**；下架书重录同 ISBN 时业务层提示"已存在下架图书，可恢复上架"而非报错 | A 原方案是 ACTIVE 范围内业务校验；全局唯一防脏数据更简单 | A 改一处校验逻辑 |
| D6 | 枚举值统一小写（见 G3） | 两边机械替换 | 双方各改常量 |
| D7 | readers.user_id 关联保留（B 已建）；A 的删除校验、C 的资格判断不受影响 | 个人中心必需 | 无 |
| D8 🔴 | 参数键名采纳 B：`borrow_period_days=30 / borrow_limit=5 / max_renew_times=? / reservation_hold_days=3 / renew_period_days=15`；**默认 max_renew_times 取值需拍板**（A 默认 2，B 默认 1） | 键名用 B 的；默认值建议 2（需求未规定，倾向宽松） | B 键名不动；A 改常量 |
| D9 | 借出/应还/归还三列改 DATE 类型（见 G4） | 逾期天数=DATE 差，直接可比 | 双方微调 |
| D10 | "一副本一有效借阅"数据库层实现：采纳 B 的生成列 + UNIQUE（MySQL 无部分索引），SQLite 侧 A 保留部分索引等价实现 | 双方言并存，语义一致 | 文档写清即可 |
| D11 | 表名以 B 为准（A 的 copies→book_copies、borrow_records→loans 改名） | B 脚本已入库不动，A 机械替换表名 | A 改 SQL 字符串 |

## 四、给 B 的三个问题（已从代码自答两个，剩一个待确认）

1. ✅ **驱动**：`common/database.cpp` 用 **QODBC + ODBC 数据源**（非 QMYSQL 插件）——A 适配时走同一路线，**无需编译 QMYSQL 插件**，工作量比预估更小；
2. ✅ **连接参数**：DSN（默认 `LibraryManagerDSN`）+ 环境变量 `LIBRARYMANAGER_DB_USER` / `LIBRARYMANAGER_DB_PASSWORD` / `LIBRARYMANAGER_DSN`；库名 `library_manager`（正式）/ `library_manager_smoke`（冒烟）；字符集 utf8mb4；
3. ⚠️ **待确认**：`database.cpp` 连接校验只数了 **8 张表（漏了 reservations）**——是有意为之还是遗漏？另外确认实际库中表结构与迁移脚本完全一致。

## 五、新发现的联调风险（实测验证）

| 编号 | 风险 | 说明 | 建议 |
|---|---|---|---|
| R1 🔴 | **ANSI ODBC 驱动的中文乱码** | B 的连接串 `CHARSET=gb18030`，init 脚本注释明确"ANSI ODBC 驱动会弄坏中文"并用 UTF-8 hex 技巧绕过（仅建库场景）。A 板块运行时要读写中文书名/作者/分类，QSqlQuery 预处理语句经 ANSI 驱动很可能乱码 | 联调第一件事：中文读写往返实测。若乱码，候选方案：换 Unicode ODBC 驱动（MySQL Connector/ODBC 的 Unicode 版）或 DSN 连接串改 utf8 |
| R2 | 表校验清单与迁移脚本不一致 | 连接层校验 8 表，迁移脚本建 9 表 | B 统一（建议校验也查 9 张） |
